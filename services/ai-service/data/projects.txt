1. BluHorizon AI - Full-Stack RAG Application
   Language: Python | repo: BluHorizon-AI-drm
################################################################

WHAT IT IS
A full-stack Retrieval-Augmented Generation (RAG) application I designed
and built. A user ingests documents (PDF, DOCX, XLSX); the system chunks
and embeds them into a FAISS vector store, and the user queries that
corpus through an AI chat interface backed by the Anthropic Claude API.
The whole thing is containerized and runs with Docker Compose.

ARCHITECTURE (from the repo)
docker-compose.yml orchestrates two services:
  - Backend (port 8000)
      routers/   -> chat, RAG, and agent endpoints
      services/
        rag_pipeline.py        -> the HyDE-based RAG pipeline
        embedding.py           -> vector embedding generation
        store_faiss_vector.py  -> FAISS vector store operations
        sqlite.py              -> SQLite integration
  - Frontend (port 3000)
      a Flutter (Dart) mobile app

THE INTERESTING ENGINEERING
- HyDE retrieval pipeline (Hypothetical Document Embeddings): instead of
  embedding the raw user question and searching with it, the system first
  asks the model to generate a hypothetical answer, then embeds THAT and
  uses it for semantic retrieval. The intuition is that a hypothetical
  answer lives closer in embedding space to the real answer passages than
  the question does, so recall improves. This is a genuinely non-trivial
  retrieval technique, not just "embed and top-k."
- Gap-aware chunk filtering: rather than always returning a fixed number
  of chunks (top-k), it looks at the similarity scores and uses a dynamic
  score-gap cutoff, keeping chunks until there is a meaningful drop in
  relevance. This avoids stuffing the context with weak matches.
- Document ingestion across multiple formats (PDF, DOCX, XLSX) into a
  unified embedding store.
- Web-search augmentation via the Tavily API for queries that benefit
  from fresh external information.

TECHNICAL STACK
  Backend:         Python, FastAPI, Uvicorn
  AI:              Anthropic Claude API
  Vector search:   FAISS (CPU)
  Embeddings:      Sentence-Transformers
  ML utilities:    PyTorch, tiktoken (tokenization / token counting)
  External search: Tavily API
  Persistence:     SQLite / Firebase (per repo); migrated to PostgreSQL
                   (per current resume)
  Frontend:        Flutter (Dart), mobile-first
  Container:       Docker, Docker Compose

WHAT I LEARNED
With RAG, the model is rarely the hard part; retrieval and data are. The
bulk of the engineering, and the bulk of the quality, lived in the HyDE
pipeline and the gap-aware filtering, i.e. in how queries get turned into
the right context, not in the call to the LLM. That lesson shapes how I
think about applied AI generally: the infrastructure around the model is
where the real work is.

INTERVIEW TALKING POINTS
- Explain HyDE and why it beats naive query embedding (recall).
- Explain the dynamic score-gap cutoff vs. fixed top-k (precision /
  context quality).
- Walk the request path: question -> HyDE answer -> embed -> FAISS search
  -> gap filter -> context -> Claude -> response.

The repo README documents a Flutter frontend and SQLite/Firebase storage.
The resume says FastAPI + PostgreSQL with 45 automated tests. If the

2. Boggle Buddies - Real-Time Multiplayer Word Game
   Language: Java (primary) | repo: boggle-app
################################################################

WHAT IT IS
A real-time multiplayer word game inspired by Boggle, built by a Scrum
team of six. Players race to find valid words on a randomly generated
letter board within a time limit. It supports live multiplayer matches
AND a player-vs-computer mode, with guest play or registered accounts
that track long-term stats (wins/losses).

GAMEPLAY SYSTEMS (from the spec/README)
- Board-shuffling algorithms to generate the randomized letter grid.
- Dictionary-based word validation (is this a real word?).
- Rule enforcement, e.g. no duplicate words within a match.
- A dynamic scoring screen that distinguishes UNIQUE words (only you
  found them) from SHARED words (multiple players found them), which is a
  real scoring-logic detail, not just a point tally.
- Settings customization for matches.
- Real-time game synchronization so all players see the same state live.
- Persistent storage of accounts and stats.

ARCHITECTURE

               controller -> service -> repository layering
  Real-time:   WebSockets layer for live multiplayer sync
  Database:    SQL (relational), for accounts and stats
  Container:   Docker (Dockerfile in repo)
  Testing:     128 unit tests
  CI/CD:       throughout the project

DEPLOYMENT (per resume)

  - Frontend and backend Deployments behind Kubernetes Services
  - ConfigMaps and Secrets externalize database configuration
  - Helm used to install the External Secrets Operator, which syncs
    credentials from AWS Secrets Manager via an IAM role for
    KMS-encrypted storage
  - AWS certificates configured for HTTPS on a custom domain

LANGUAGE BREAKDOWN IN REPO
  Java ~226k, JavaScript ~75k, CSS ~30k, Dockerfile, HTML.

WHY THIS PROJECT MATTERS
This is my most complete full-stack project. It has a real layered

4. QOI Image Codec - CPU & GPU Acceleration Study (Capstone)
   Language: C++ | repo: ece455-qoi
################################################################

WHAT IT IS
A performance-focused implementation and benchmarking study of the QOI
(Quite OK Image) lossless image format, built as my ECE capstone. I
implemented the codec in multiple variants and benchmarked encode/decode
throughput across all of them on HPC hardware.

THE FOUR (FIVE) VARIANTS
  reference/    -> baseline, no parallelism
  single-cpu/   -> single-threaded CPU
  multi-cpu/    -> multi-threaded CPU using OpenMP
  gpu-cuda/     -> CUDA GPU kernels
  gpu-segment/  -> segmented CUDA approach
Having a clean baseline plus progressively parallelized versions is what
makes the benchmarking meaningful, you can attribute speedups to specific
techniques.

RESULTS
  - 10x encoding speedup with OpenMP (multi-core CPU)
  - 5.9 GB/s GPU decode throughput vs. 4.2 GB/s on CPU

HOW QOI WORKS (and why parallelizing is hard)
QOI encodes losslessly using a small operation set:
  OP_INDEX -> reference a pixel from a 64-entry running hash table
  OP_DIFF  -> small per-channel RGB delta from the previous pixel
  (plus run-length and full-color ops)
The catch: the running hash table and the "previous pixel" both create
data dependencies between consecutive pixels. Naive parallelism breaks
correctness because each pixel's encoding depends on prior state. The
interesting engineering is restructuring the work (e.g. segmenting) so it
can be parallelized while still producing correct, lossless output.

TECHNICAL STACK
  Language:     C++20
  GPU:          CUDA (NVIDIA)
  CPU parallel: OpenMP
  Libraries:    libpng, STB image
  Build:        GNU Make (with CUDA support)
  HPC:          SLURM job scheduler for benchmarking runs

LANGUAGE BREAKDOWN IN REPO
  C++ ~92k, CUDA ~26k, Shell, Makefile.

WHY THIS PROJECT MATTERS
This is my strongest systems-and-performance project: real GPU
programming, real CPU parallelism, careful reasoning about data
dependencies, and measured results on cluster hardware. For any
systems/performance/infra role, this is the project to lead with, and it
also pairs with the NVIDIA CUDA certificate from GTC.

INTERVIEW TALKING POINTS
- Why the hash table + previous-pixel state make naive parallelism
  incorrect, and how segmentation addresses it.
- The difference between the OpenMP and CUDA approaches.
- How you benchmarked fairly (baseline -> variants) on SLURM.

5. RISC-V Superscalar Pipelined Processor
   Language: Verilog/SystemVerilog | repo: processor_RISCV_321
################################################################

WHAT IT IS
A superscalar RISC-V pipelined processor implemented in hardware
description language. This is digital design at the register-transfer
level: I defined the actual logic of a CPU, not software running on one.

WHAT I BUILT (per resume + repo composition)
  - All five classic pipeline stages (fetch, decode, execute, memory,
    writeback)
  - Data forwarding to resolve pipeline hazards (so dependent
    instructions do not stall unnecessarily)
  - Multi-issue SUPERSCALAR execution: issuing more than one instruction
    per cycle, which is substantially more complex than a single-issue
    pipeline (you must handle structural and data hazards across parallel
    issue slots)
  - A cache system for both instruction and data memory

The repo also contains a large amount of Assembly (~52k), which are the
test programs exercising the processor, and Makefile-driven simulation.

LANGUAGE BREAKDOWN IN REPO
  Verilog ~198k, Assembly ~52k, SystemVerilog ~14k, Makefile.

WHY THIS PROJECT MATTERS
Superscalar execution is genuinely advanced for a student processor, most
course processors are single-issue. Building multi-issue with forwarding
and caches shows real depth in computer architecture and digital design.
Together with the Segway ASIC, this is the foundation of my Computer
Engineering identity: the lowest level of the stack, where you design the
hardware itself.

INTERVIEW TALKING POINTS
- Why superscalar issue is hard (hazards across parallel issue slots).
- How data forwarding avoids stalls.
- The instruction/data cache design.
- Writing Assembly test programs to validate the pipeline.

6. Self-Balancing Segway ASIC
   Language: SystemVerilog | repo: Segway
################################################################

WHAT IT IS
A complete RTL-to-gates self-balancing Segway controller, designed in
SystemVerilog for a digital system design and synthesis course. It is a
full real-time control SYSTEM realized in hardware, taken all the way from
RTL through synthesis to a gate-level netlist.

SUBSYSTEMS (per resume)
  - PID pitch balance control (the core control loop that keeps it
    upright)
  - Differential PWM motor drive (drives the two motors, including
    steering via differential output)
  - A2D (analog-to-digital) interface
  - SPI interface to an inertial sensor / IMU (reads pitch/motion)
  - UART command receiver (accepts external commands)
  - A steering-enable finite state machine

SYNTHESIS & VERIFICATION
  - Synthesized to a gate-level netlist targeting a 333 MHz clock
  - Tool: Synopsys Design Compiler
  - Standard-cell library: SAED32 (32nm)
  - Verified with 10+ ModelSim testbenches covering balance response,
    steering, and an overcurrent safety cutoff
The repo also includes Python (~5k), likely modeling/stimulus or analysis
scripts supporting verification.

LANGUAGE BREAKDOWN IN REPO
  SystemVerilog ~201k, Python ~5k.

WHY THIS PROJECT MATTERS
This is real-time control implemented in hardware, including the sensor
interfaces (SPI IMU, A2D), the control loop (PID), the actuation
(differential PWM), and safety logic (overcurrent cutoff), then pushed
through actual synthesis to gates at a real clock target. The PID + IMU +
real-time-control aspects are directly relevant to robotics and embedded
systems. It proves you can go from a control problem all the way to
silicon-ready logic.

INTERVIEW TALKING POINTS
- The PID balance loop and reading the IMU over SPI.
- Differential PWM for combined drive + steering.
- The overcurrent safety FSM.
- Taking it through Synopsys DC synthesis at 333 MHz on SAED32, and what
  hitting a timing target means.
